# Week 6 — pull requests, one per slice

The brief's GitHub deliverable: *"Public; per-slice branches preserved; each PR
description lists which acceptance criterion that slice advances and confirms the
fitness test passed."*

**Why these are the PRs and not earlier ones.** All four pre-existing branches
(`feat/w6-foundation`, `feat/w4-implementation`, `docs/orientation`, `docs/w6-defense`)
have **0 commits not in `main`** — they are fully merged, so GitHub has nothing to
compare and no PR can be opened from them. Retroactive PRs are not possible, and
fabricating branch history to produce them would be worse than the gap. The clause is
therefore satisfied going forward, with the seven slices below.

Open each against the branch beneath it (a stack), then merge bottom-up.

---

## 1. `feat/w6-cat4-gate-close` → `main`

**Acceptance criterion advanced.** MVP A9 — *"per-route query counts within +10% of the
Part 1 baseline."* This is the clause the reviewer failed the submission on: it had been
measured for one of five flows and recorded as met for all five.

**What changed.** All five Part-1 flows measured — main page 57→46, document 64→54,
issues 61→41, week board 67→48, search 57→53. Flow definitions are now generated by
`bench/cat4-queries/capture_flows.mjs` rather than hand-traced, so the gap cannot
silently reopen. Also fixes 21 failing tests (cli 3, slack 18) whose harnesses had
drifted from the signature contract, and corrects six ledger rows that claimed more than
their evidence showed.

**Fitness tests confirmed passing.** `contract.fitness.test.ts`, `sdk-parity.test.ts`
(both directions, non-vacuous). Suites: api 880 · web 163 · sdk 82 · cli 76 · slack 64
= 1,265 green. Category-4 harness: two independent passes agreeing exactly, 77 URLs all
HTTP 200, audit-era control still returning exactly 32.

## 3. `ci/drill-on-every-pr` → `ci/run-cli-slack-suites`

**Acceptance criterion advanced.** Signature Challenge, Required Capabilities —
*"Drill runs in CI on every PR. Any regression past the configured threshold fails the
build."* The ledger claimed this and cited `verify-deployment`, which is gated to `main`
and had never run on a PR.

**What changed.** A new `drill-pr` job boots Ship from the PR's own build against a
`postgres:16` service and drills that. The existing `main` gate stays — that job targets
live prod, which only reflects `main`, so a PR run there would report a green that means
nothing. Same binary, same 60 s threshold, same non-zero exit.

**Fitness test confirmation.** Workflow YAML validated (13 steps). **The proof this clause holds is this PR's own CI run — it has not happened yet, and the row stays PARTIAL until it does.** An audit found the first version of this job could never have worked: migration 043 mints the drill app by copying the *production* grader app's secret hash, keyed on a hardcoded prod `client_id`, so on any fresh database it matches zero rows. A new `seed:drill-app` script registers the app explicitly instead.

## 4. `fix/devportal-replay-app-id` → `ci/drill-on-every-pr`

**Acceptance criterion advanced.** Testing Scenario 8 — *"Click 'Replay' against a
now-healthy subscriber and verify the replay succeeds with the original idempotency key
intact."*

**What changed.** `e2e/devportal-replay.spec.ts` is the first test to click anything in
the dev portal, and it immediately caught a live defect: `useReplayDelivery` never sent
`app_id`, so **every click returned `400 validation_failed`**. Fixed. The API-level
idempotency drill covered the contract and passed throughout — nothing it asserts can
see a client that never reaches the endpoint.

**Fitness test confirmation.** New spec passes; asserts the database wrote exactly one
replay row carrying the original idempotency key, then that the portal renders the
chain. Web suite still 163 green.

## 6. `fix/prove-live-c7-authenticated` → `feat/terraform-ecs-topology`

**Acceptance criterion advanced.** Performance Targets — *"Public API responses with
rate-limit headers: 100%."*

**What changed.** The live `c7` probe requested `/api/v1/me` **unauthenticated** and
demanded three `x-ratelimit-*` headers, so it could never pass — and the ledger cited it
as proof the headers ship. The brief's own wording settles it: *"per-app and per-token
token-bucket limits"* means a request with no identity has no bucket, and it 401s before
the limiter runs. `c7` now authenticates first, and records SKIPPED rather than MISSING
when no secret is available — "could not run" is a different claim from "failed".

**Fitness test confirmation.** `prove-live.spec.ts` passes; c1–c6 and c8 MET, c7 SKIPPED
locally with the unauthenticated control observation recorded.

## 7. `docs/w6-requirement-closure` → `fix/prove-live-c7-authenticated`

**Acceptance criterion advanced.** Submission — requirement-to-evidence traceability.

**What changed.** Ledger and traceability updated to what now exists, then corrected
again by two independent audits. **Twelve** brief clauses had zero rows and are traced
for the first time (sections J, K, L — Interface Definitions, the drill-stage table, and
the technical-stack clauses). Section E had no Status column, so a script counting the
file inferred MET for nine rows.

**Fitness test confirmation.** Counts computed from the file's own tables: **105 rows,
92 MET / 9 PARTIAL / 3 OWED / 1 ACCRUING / 0 MISSING**. The PARTIAL count went **up**,
from 2 to 9, because the audit found rows softer than the brief — a PKCE "P95" that was
a file duration, a webhook "P95" that was one sample, a TTFE "clean container" install
measured at 1 ms. That direction is the point.
