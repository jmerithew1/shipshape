# Cat 3 after-capture notes — 2026-07-29

## Incident disclosure

Between the `rebaseline-16a351b` capture and the after-captures, `pnpm -C api test` was run
directly and **TRUNCATEd the `ship_dev` database** — `api/src/test/setup.ts` truncates 15 tables
against whatever `DATABASE_URL` points at, with no test-database guard (the audit avoided this by
pointing tests at a throwaway `ship_test`; the audit's Cat-5/6 findings flagged the hazard class).
No measurements ran against the wiped database (the login failure blocked the capture). The database
was restored with `pnpm db:seed` + `bench/seed/seed_volume.sql` and verified to match the pinned
conditions **exactly**: 557 documents / 23 users / 254 issues / 35 sprints / 551 associations.
A guard fix is part of the Cat-6 workstream.

## Interpretation

- **The throttle's effect is cleanest on `/api/auth/me`** (the endpoint that is almost pure auth
  tax): P95 −47% to −63% at c=10 and −27% to −45% at c=25, consistent across both runs.
  **Category-3 target met on this endpoint.**
- **The degraded endpoints are confounded by the database restore, not caused by the fix.** The
  throttle only removes a write; it cannot slow a read-heavy endpoint by 60%. `/api/issues` and
  `/api/accountability/action-items` read the freshly bulk-inserted tables, whose planner
  statistics were stale right after the restore (the rebaseline database had long-settled stats).
  Both degrade most in run #1 and recover toward baseline in run #2 as autoanalyze catches up —
  the signature of plan-quality drift, not a code regression.
- `ANALYZE` was run on `ship_dev` **after** run #2 (never between paired captures) to restore
  settled statistics for subsequent measurements.
- The second ≥20% endpoint comes from a targeted fix of the audit's confirmed N+1
  (`api/src/services/accountability.ts`, five per-row loops), measured as a fresh
  `rebaseline2 → after` pair on the restored+analyzed database so both sides share identical
  conditions.

## Second-endpoint attempts (3 used — item parked with evidence)

Target: ≥20% P95 on a second endpoint (first: /api/auth/me, met consistently).

1. **Accountability N+1 batch** (`5d55ac8`): 5 per-row loops collapsed. Query-count
   reduction is real; latency pair (rebaseline2-9c00675 → after-n1/after-n1b) is flat at warm
   server (−3%/−1.7%) — at seed cardinality the batched queries were ~1–3 ms of an ~85 ms request.
2. **Issues list content drop** (`b349a63`): payload only fell 223.1 → 212.4 kB — at this seed,
   issue content is ~10 kB of the payload; `properties` and row overhead dominate. Architecturally
   correct (content grows unbounded in real use), unprovable as a latency win here.
3. **EXPLAIN ANALYZE of the full list query: 1.132 ms execution.** The database is not the
   bottleneck; ~150 ms/request is Node-side work (JSONB row parsing, mapping, JSON serialization,
   event-loop queueing under dev-mode tsx). A provable ≥20% would require pagination (an API
   semantics change) or production-mode measurement (outside the pinned dev-mode conditions).

Identical-code runs tonight varied ±20% P95 (e.g. issues c=10: 197→244→216→206→151→189), so only
structural wins ≥~2× the noise floor (like auth/me's −50%) are honestly provable per-endpoint.
Status: Cat 3 = target met on 1 of 2 endpoints; second endpoint parked with this diagnosis.

## 2026-07-30 — second endpoint MET: /api/projects grouped-join rewrite

The parked item above is now closed by a fourth, mechanism-guided fix. EXPLAIN showed /api/projects
was the one endpoint that is genuinely DB-bound: three correlated subqueries per project row
(sprint count, issue count, allocation-derived inferred status) — the audit's slowest main-page
query. All three were rewritten as two grouped LEFT JOINs computed once per request, with the CASE
semantics of inferred status preserved (api suite 453/453, projects tests 14/14).

concurrencies, well past target and above the ±20% noise floor:
